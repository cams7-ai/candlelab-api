# Prompt de implementação — CandleLab API

Implemente **CandleLab API**, o backend de um laboratório local de backtest histórico para Binance Spot. Trabalhe em um repositório próprio, `candlelab-api`, com configuração, dependências, testes, README e Docker Compose próprios. A API deve inicializar, importar datasets e executar backtests via HTTP sem depender do repositório do frontend. O frontend independente **CandleLab Web** usa o contrato HTTP v1 abaixo.

## Arquitetura e referência

Use o [ReplayQuant](https://github.com/cams7-ai/replayquant) como referência técnica. Antes de implementar, inspecione o README, o código do motor e os testes relevantes. Consulte as especificações das [Sprints 08](https://github.com/cams7-ai/replayquant/blob/main/docs/sprint08.md), [10](https://github.com/cams7-ai/replayquant/blob/main/docs/sprint10.md), [11](https://github.com/cams7-ai/replayquant/blob/main/docs/sprint11.md) e [13](https://github.com/cams7-ai/replayquant/blob/main/docs/sprint13.md) para métricas, indicadores, instrumentos e datasets históricos. Registre no README o commit consultado e as regras reaproveitadas ou adaptadas. Se aproveitar código, confira a licença e preserve os avisos aplicáveis.

- Use **Python 3.11+**, FastAPI, Pydantic, PyMongo e redis-py. Separe domínio, aplicação e infraestrutura. O motor deve executar em memória, sem dependência de HTTP, MongoDB ou Redis.
- Entregue Docker Compose próprio para API, worker, MongoDB e Redis, com versões fixadas, health checks e volume para MongoDB. Inclua `.env.example`, configure as origens CORS por ambiente e documente a porta local da API, com padrão `8000`.
- MongoDB é a fonte de verdade. Redis é cache descartável com TTL para leituras derivadas, como páginas de candles imutáveis. Leia ou reconstrua pelo MongoDB se o cache estiver indisponível. As tarefas e resultados duráveis permanecem no MongoDB.
- O escopo é local, monousuário e Spot. Todas as negociações são simuladas. O acesso externo à Binance é necessário apenas na aquisição sob demanda. Upload e backtests sobre datasets gravados funcionam offline.

## Aquisição e importação de candles

Aceite upload com arquivo JSON, símbolo e intervalo obrigatórios. Normalize o símbolo para maiúsculas. Exiba o par como `BTC/USDT` ou `ETH/USDT`. Use um catálogo simples com ativo base, moeda de cotação e intervalos aceitos, extensível por configuração para outros pares Spot cotados em USDT. Suporte pelo menos `1m` e `5m` e exponha os valores aceitos no catálogo da API.

Aceite o formato de resposta de klines Spot da Binance, um array JSON de arrays com exatamente 12 posições. A ordem dos campos é:

| Índice | Campo | Tipo no JSON |
| --- | --- | --- |
| 0 | Abertura em milissegundos UTC | Inteiro |
| 1 | Preço de abertura | String decimal |
| 2 | Preço máximo | String decimal |
| 3 | Preço mínimo | String decimal |
| 4 | Preço de fechamento | String decimal |
| 5 | Volume no ativo base | String decimal |
| 6 | Fechamento em milissegundos UTC, inclusivo | Inteiro |
| 7 | Volume na moeda de cotação | String decimal |
| 8 | Número de negociações | Inteiro |
| 9 | Volume comprador agressor no ativo base | String decimal |
| 10 | Volume comprador agressor na moeda de cotação | String decimal |
| 11 | Campo reservado da Binance | String, preserve o valor |

Confira [o contrato de klines da Binance Spot](https://developers.binance.com/docs/binance-spot-api-docs/rest-api/market-data-endpoints#klinecandlestick-data). O array não contém símbolo ou intervalo. Use o símbolo informado na requisição como metadado, confira o intervalo por timestamps, e trate o nome do arquivo como informação de exibição.

Valide tamanho do upload e quantidade máxima de candles com limites configuráveis. Valide JSON, tipos estritos, números finitos, timestamps inteiros e válidos, janela alinhada em UTC, preços positivos, volumes e contagem não negativos, e `low <= min(open, close) <= max(open, close) <= high`. Para os intervalos fixos aceitos, exija `close_time_ms = open_time_ms + duração_ms - 1`. Exija abertura estritamente crescente e continuidade entre linhas. Em erro de linha, informe índice, campo e motivo. Rejeite duplicatas, conflitos e lacunas com diagnóstico. Preserve os candles exatamente no período do conteúdo. Quando a API aceitar filtros de data, use o intervalo semiaberto `[início, fim)`.

Grave cada candle e os metadados da importação, incluindo origem `BINANCE_SPOT`, hash canônico dos candles normalizados, símbolo, intervalo, quantidade, primeira e última abertura e horário da importação. Registre a procedência de cada aquisição, com modo `UPLOAD` ou `BINANCE_API`, nome e SHA-256 do arquivo quando houver upload, ou parâmetros efetivos da consulta quando for via API. Se os dois modos resultarem no mesmo snapshot, reutilize o dataset e preserve os metadados de procedência de ambos. Repetir a importação do mesmo conteúdo normalizado para a mesma origem, par e intervalo deve devolver o dataset existente, inclusive sob concorrência. Um conteúdo diferente forma outro snapshot. Use índice único em `(dataset_id, open_time_ms)` e identidade única do dataset por origem, par, intervalo e hash normalizado. Valide antes de publicar e só disponibilize datasets completos. Implemente estado de importação e retomada ou limpeza de gravações parciais sem expor candles incompletos como dados válidos. Guarde candles em documentos individuais e grave em lotes.

### Consulta direta à Binance Spot

Na rota de consulta direta à Binance, exija apenas `symbol` e `interval`.

| Parâmetro | Obrigatório | Tipo e formato enviados pelo frontend | Exemplo |
| --- | --- | --- | --- |
| `symbol` | Sim | String com símbolo disponível no catálogo | `BTCUSDT` |
| `interval` | Sim | String com intervalo aceito | `5m` |
| `startTime` | Não | String ISO 8601 UTC no formato `YYYY-MM-DDTHH:mm:ssZ` | `2026-08-19T00:00:00Z` |
| `endTime` | Não | String ISO 8601 UTC no formato `YYYY-MM-DDTHH:mm:ssZ` | `2026-08-22T00:00:00Z` |
| `limit` | Não | Inteiro de 1 a 1000 por requisição | `1000` |

O frontend deve enviar datas como strings, por exemplo `2026-11-14T17:11:39Z`, com segundos e o sufixo `Z`. Valide no backend o formato e a validade do calendário, rejeitando datas sem UTC explícito, formatos inválidos e timestamps anteriores à época Unix. Compare `startTime <= endTime` somente quando os dois estiverem presentes. A consulta considera a abertura do candle e inclui uma abertura exatamente em `endTime` se o candle estiver fechado. Os filtros de leitura de datasets continuam usando `[início, fim)`.

Faça a requisição HTTP no backend para o endpoint público fixo `https://data-api.binance.vision/api/v3/klines`. O backend converte somente as datas presentes em milissegundos Unix ao montar a query e omite parâmetros opcionais ausentes. Quando `limit` for omitido, use o comportamento padrão da Binance, que retorna até 500 candles por requisição.

Inclua no README os dois exemplos de JSON aceitos por `POST /api/v1/datasets/binance`:

```json
{"symbol":"BTCUSDT","interval":"5m"}
```

```json
{"symbol":"BTCUSDT","interval":"5m","startTime":"2026-08-19T00:00:00Z","endTime":"2026-08-22T00:00:00Z","limit":1000}
```

O segundo exemplo corresponde à chamada externa abaixo:

```bash
curl --request GET --url 'https://data-api.binance.vision/api/v3/klines?symbol=BTCUSDT&interval=5m&startTime=1787097600000&endTime=1787356800000&limit=1000'
```

Consulte a [documentação geral da API Spot da Binance](https://developers.binance.com/docs/binance-spot-api-docs/rest-api) e o [contrato de klines](https://developers.binance.com/docs/binance-spot-api-docs/rest-api/market-data-endpoints#klinecandlestick-data). Se faltar uma ou ambas as datas, consulte uma única página. Sem datas, a Binance retorna os candles mais recentes. Só com `startTime`, retorna os primeiros candles a partir do início. Só com `endTime`, retorna os candles mais recentes até o fim informado.

Com as duas datas, pagine se necessário, mantendo o `endTime` e o `limit` informado, ou omitindo `limit` em todas as páginas se ele estiver ausente. Avance `startTime` para a última abertura recebida mais a duração do intervalo. Pare ao ultrapassar `endTime` ou receber uma página vazia. Se a paginação deixar de avançar ou se o total ultrapassar o limite de aquisição configurado, informe o erro e preserve a integridade do dataset.

Use timeout e retentativas limitadas para erros transitórios, respeitando `Retry-After` quando indicado. Informe indisponibilidade, resposta inválida e período sem candles fechados. Considere apenas candles totalmente fechados no momento da aquisição. Valide a sequência completa, inclusive entre páginas, e aplique o mesmo parser, normalização e processo de publicação do upload. Após a gravação no MongoDB, devolva o dataset publicado com os metadados do contrato. Se a consulta falhar durante a paginação, nenhum dataset parcial deve ficar disponível.

### Caso de aceitação do anexo

Use `candles-btcusdt-spot-5m_2026-08-19T0000Z_a_2026-08-22T0000Z.json` fornecido como entrada. Com `BTCUSDT` e `5m`, o upload deve resultar em **865 candles**, com primeira abertura `2026-08-19T00:00:00Z` e última abertura `2026-08-22T00:00:00Z`. A última linha fecha em `2026-08-22T00:04:59.999Z` e faz parte do arquivo. O mesmo upload com `1m` deve retornar erro de intervalo, sem publicar outro dataset. Se o arquivo não estiver no checkout, documente onde fornecê-lo para a verificação e mantenha uma fixture sintética pequena para testes automatizados.

## Sessões e processamentos

vincula um único dataset, um nome, caixa inicial em USDT e taxa proporcional por execução. Exija caixa inicial positivo e taxa em `[0, 1)` no backend. Armazene o dataset e os parâmetros da sessão de forma estável para permitir novas execuções e consulta após reinício. Alterações na configuração financeira exigem uma nova sessão.

Um **processamento** é uma execução de uma estratégia simples ou combinada sobre os candles da sessão. Cada execução começa com o mesmo caixa inicial e posição zero. Seu caixa, posição, indicadores e resultados são independentes dos demais processamentos. Use versões explícitas da estratégia, da política de execução e do motor. Grave um snapshot dos parâmetros efetivos, do dataset/hash e da política em cada execução.

Persista datasets, candles, sessões, execuções, sinais, fills, ledger, indicadores, pontos da curva patrimonial e resumo no MongoDB. Use índices pelos identificadores e pela ordenação das consultas. Divida séries e eventos grandes em documentos pagináveis para evitar ultrapassar o limite por documento.

O worker deve consumir tarefas registradas no MongoDB, com estados `queued`, `running`, `completed` e `failed`. Use tomada atômica, prazo de posse renovável e identificador de tentativa. Permita recuperar a tarefa se o worker cair. Isole resultados por tentativa e publique apenas a tentativa concluída mediante atualização condicional que valide a posse. Uma tentativa antiga que retome não pode publicar sobre a atual. Aceite chave de idempotência por sessão na criação da execução, com conflito claro se a mesma chave chegar com outros parâmetros. Exponha o estado para polling e forneça mensagem de falha adequada para exibição.

## Indicadores e sinais

Implemente um registro explícito de estratégias com nome, versão, validação de parâmetros e interface incremental equivalente a `on_close(candle)`. A estratégia produz valores dos indicadores, prontidão, sinal opcional e motivo. O motor financeiro recebe o sinal e aplica a mesma política de execução para todas as estratégias. Documente como cadastrar uma nova estratégia e seus parâmetros sem alterar esse motor.

| Estratégia inicial | Regra de sinal | Parâmetros padrão |
| --- | --- | --- |
| `SMA_CROSS@1` | BUY no cruzamento da SMA curta de baixo para cima da longa. SELL no inverso. | Curta 9, longa 21 |
| `EMA_CROSS@1` | Mesmo predicado de cruzamento, aplicado às EMAs. Inicie cada EMA com a SMA de sua janela e aplique `alpha = 2 / (N + 1)`. | Curta 9, longa 21 |
| `RSI_REVERSION@1` | BUY quando o RSI sai da sobrevenda, de `<= oversold` para `> oversold`. SELL quando sai da sobrecompra, de `>= overbought` para `< overbought`. | Período 14, limiares 30 e 70 |
| `SMA_RSI_FILTER@1` | BUY quando a SMA cruza para cima e o RSI do mesmo fechamento é maior ou igual ao limiar de confirmação. SELL no cruzamento da SMA para baixo. | SMA 9/21, RSI 14, confirmação 50 |

Use somente preços de fechamento observados. Nos cruzamentos de SMA/EMA, a comparação anterior admite igualdade e a atual exige cruzamento estrito. Exija duas observações consecutivas prontas para comparar. Para o RSI, use a média simples das primeiras N variações como semente e a suavização de Wilder nas seguintes. RSI é 50 se ganhos e perdas médios forem zero, 100 se só as perdas forem zero e 0 se só os ganhos forem zero. A primeira observação calculável do RSI exige N+1 fechamentos. Nos indicadores em aquecimento, exponha o estado sem desenhar zeros artificiais. Na estratégia combinada, a compra exige o RSI já calculado no fechamento do cruzamento. A regra de saída depende apenas da SMA.

Valide parâmetros, como janelas inteiras com `1 <= curta < longa`, período positivo e `0 < oversold < overbought < 100`. Defina limites compatíveis com a carga aceita e informe aquecimento insuficiente. Use aritmética determinística com política de precisão explícita e versionada, incluindo a das recorrências. Arredondamento de exibição não deve influenciar a emissão do sinal. Persista o vínculo entre avaliação, sinal, decisão e preenchimento quando houver.

## Evolução das estratégias

Inclua novas estratégias individuais e novas combinações em versões futuras. Exemplos de evolução são rompimento de Donchian, Bandas de Bollinger, MACD e Supertrend, além de Donchian + volume e Supertrend + RSI. A primeira versão entrega as quatro opções da seção anterior.

Cadastre cada nova estratégia ou combinação como uma opção versionada no backend. Reutilize os cálculos dos indicadores, a interface incremental e o motor financeiro existente. Para cada combinação, defina explicitamente o gatilho de entrada, as confirmações ou filtros e a regra de saída. Use somente dados disponíveis no instante da decisão. Publique os parâmetros e valores padrão em `GET /api/v1/strategies`, preserve o catálogo das versões anteriores necessário para reproduzir os resultados e guarde no processamento a versão e os parâmetros efetivos.

## Simulação e resumo financeiro

- Observe o candle no fechamento, gere a decisão e execute na abertura do candle imediatamente seguinte. Registre timestamp de abertura do candle usado para plotar o sinal e instante em que ele ficou disponível. Registre o timestamp e preço do fill separadamente. Um sinal no último candle fica sem execução, com motivo `NO_FUTURE_OPEN`.
- Uma posição comprada por execução. BUY usa o caixa disponível, descontando a taxa antes de determinar a quantidade. Use `quantidade = floor_to_step(caixa / (preço × (1 + taxa)))`. Defina um passo simulável por instrumento, versionado e informado no relatório. Quantidade nula, compra com posição aberta e venda sem posição geram diagnóstico. Na venda, liquide toda a posição. O preço usado é a abertura seguinte, com slippage zero nesta versão.
- Calcule `bruto = quantidade × preço` e `taxa = bruto × fee_rate` nas duas pontas, em USDT. A compra debita bruto mais taxa e a venda credita bruto menos taxa. Atualize o ledger somente com fills efetivos e garanta caixa e posição não negativos.
- Use `Decimal` para valores financeiros e serialize-os como strings decimais canônicas na API e na persistência, com limites e precisão documentados. Use precisão suficiente para valores intermediários e arredonde a quantidade para baixo pelo passo antes de debitar. Mantenha os valores exatos no contrato HTTP.
- Marque posição aberta a mercado pelo fechamento de cada candle. Preserve a posição no encerramento e diferencie P&L realizado de P&L não realizado. No realizado de uma operação encerrada, desconte o custo total de entrada, incluindo taxa, do valor líquido da venda. Para a posição aberta, calcule o não realizado pelo valor marcado menos o custo de entrada com taxa, sem projetar uma taxa de saída. Verifique `patrimônio final - caixa inicial = P&L realizado + P&L não realizado`, sem descontar novamente as taxas.
- Entregue caixa inicial e final, quantidade e valor da posição final, patrimônio inicial e final, taxas pagas, P&L realizado e não realizado, retorno percentual sobre o caixa inicial, número de compras e vendas executadas, operações encerradas, taxa de acerto e drawdown máximo da curva patrimonial. Inclua caixa inicial como primeiro pico de referência no cálculo de drawdown. Taxa de acerto sem operações encerradas deve aparecer como indisponível. Mostre sinais, ordens sem execução e seus motivos no histórico.

## Contrato HTTP v1

Use este contrato na implementação e nas fixtures. A especificação OpenAPI publicada pelo backend deve refletir os mesmos nomes, tipos e rotas. Mantenha a compatibilidade das duas aplicações quando evoluir o contrato.

As rotas abaixo incluem o prefixo `/api/v1`. IDs são strings opacas. Campos financeiros, preços, quantidades, indicadores e percentuais são strings decimais, com ponto e sem notação científica. Timestamps terminados em `_ms` são inteiros Unix em milissegundos UTC. Nos parâmetros `startTime` e `endTime` da aplicação, use strings UTC no formato `YYYY-MM-DDTHH:mm:ssZ`.

| Método e rota | Entrada | Sucesso |
| --- | --- | --- |
| `GET /api/v1/instruments` | — | `200` com objeto `{items}`. Cada item tem `symbol`, `base_asset`, `quote_asset` e `intervals` |
| `POST /api/v1/datasets` | Multipart com `file`, `symbol` e `interval` obrigatórios | `200` com dataset publicado ou reutilizado |
| `POST /api/v1/datasets/binance` | JSON com `symbol` e `interval` obrigatórios. `startTime`, `endTime` e `limit` opcionais | `200` com dataset publicado ou reutilizado |
| `GET /api/v1/datasets` | Paginação | `200` com página de datasets publicados |
| `GET /api/v1/datasets/{id}` | — | `200` com dataset |
| `GET /api/v1/datasets/{id}/candles` | Paginação e recorte temporal opcionais | `200` com página de candles em ordem de abertura |
| `POST /api/v1/sessions` | `{name,dataset_id,initial_cash,fee_rate}` | `201` com sessão |
| `GET /api/v1/sessions` | Paginação | `200` com página de sessões |
| `GET /api/v1/sessions/{id}` | — | `200` com sessão |
| `GET /api/v1/strategies` | — | `200` com `{items}` |
| `POST /api/v1/sessions/{id}/runs` | `{strategy_id,parameters}` e cabeçalho opcional `Idempotency-Key` | `202` com processamento |
| `GET /api/v1/sessions/{id}/runs` | Paginação | `200` com página de processamentos |
| `GET /api/v1/runs/{id}` | — | `200` com processamento, incluindo resumo quando concluído |
| `GET /api/v1/runs/{id}/series` | `kind=indicators\|events\|equity`, paginação e recorte temporal opcionais | `200` com página de pontos da execução concluída |

- **Páginas:** `{items,next_cursor}`, com `next_cursor` string ou `null`. Aceite `cursor` e `limit` como query params. Nas séries temporais aceite `from_ms` inclusivo e `to_ms` exclusivo. O `limit` da listagem é independente do `limit` do corpo da consulta Binance.
- **Dataset:** `id`, `source`, `symbol`, `interval`, `base_asset`, `quote_asset`, `candle_count`, `first_open_time_ms`, `last_open_time_ms` e `content_hash`. **Candle:** `open_time_ms`, `close_time_ms`, `open`, `high`, `low`, `close` e `base_volume`.
- **Sessão:** `id` e os quatro campos de criação. `initial_cash` em USDT e `fee_rate` como fator decimal. Exemplo de envio para taxa de 0,1%: `"fee_rate":"0.001"`.
- **Estratégia:** `id` versionado, `name`, `parameters_schema` (JSON Schema com propriedades, tipos, limites e valores padrão) e `defaults` como objeto. IDs iniciais: `SMA_CROSS@1`, `EMA_CROSS@1`, `RSI_REVERSION@1` e `SMA_RSI_FILTER@1`. Os IDs iniciais compõem o catálogo da primeira versão. Versões futuras incluirão novas estratégias individuais e novas combinações, publicadas nesse mesmo catálogo com IDs versionados, esquema de parâmetros e valores padrão.
- **Parâmetros iniciais:** SMA e EMA usam `short_window` e `long_window` inteiros. RSI usa `period` inteiro e `oversold` e `overbought` como strings decimais. SMA + RSI usa `short_window`, `long_window` e `rsi_period` inteiros e `rsi_confirmation_min` como string decimal em `[0, 100]`. Inclua os limiares de RSI aplicáveis no gráfico a partir dos parâmetros efetivos.
- **Processamento:** `id`, `session_id`, `strategy_id`, `parameters` efetivos, `status` (`queued`, `running`, `completed`, `failed`), `summary` (objeto ou `null`) e `error` (objeto ou `null`). A estrutura de `error` é a mesma dos erros HTTP.
- **Resumo:** `initial_cash`, `final_cash`, `final_position_qty`, `final_position_value`, `initial_equity`, `final_equity`, `total_fees`, `realized_pnl`, `unrealized_pnl`, `return_pct`, `buy_fills`, `sell_fills`, `closed_trades`, `win_rate_pct` e `max_drawdown_pct`. Contagens são inteiros. `win_rate_pct` pode ser `null`. Campos `_pct` já chegam em pontos percentuais, como `"2.5"` para 2,5%.
- **Indicadores:** pontos `{open_time_ms,values}`. `values` mapeia nomes para strings decimais ou `null` durante aquecimento. Use `sma_short`, `sma_long`, `ema_short`, `ema_long` e `rsi` conforme a estratégia. **Patrimônio:** pontos `{open_time_ms,equity}`.
- **Eventos:** `id`, `seq`, `kind` (`signal`, `fill`, `skipped`), `side` (`BUY` ou `SELL`), `open_time_ms` para a âncora no gráfico, `occurred_at_ms`, `signal_id` quando aplicável, `price` e `quantity` quando preenchidos, e `reason` quando aplicável. Ordene por âncora e sequência.
- **Erros:** `{error:{code,message,details}}`. Em validação use `422` com referências aos campos ou linhas quando aplicável. Use `404` para recursos ausentes, `409` para conflito de idempotência ou séries ainda indisponíveis, e `502` ou `503` para falhas da dependência externa, conforme o caso.
